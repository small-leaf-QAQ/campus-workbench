# 数据库结构

五张表，全部在 `deploy/schema.sql` 里建好。这份文档解释每列是干什么的，以及改的时候有哪些坑。

**页面代码用的是中文字段名，数据库里是英文列名**，两者在数据层内部转换。
所以你改页面时看到的是「课程名称」，看数据库时看到的是 `name`，这是正常的。

---

## 总览

| 表 | 中文 | 一行是什么 | 主要写入方 |
|---|---|---|---|
| `courses` | 课表 | 一门课的一个时间段 | 课表页、课表截图识别 |
| `ddl_tasks` | DDL 任务 | 一个要交的东西 | DDL 页、群通知提取、机器人 |
| `plan_stages` | 长任务拆解 | 大作业里的一个阶段 | 长任务页、方案生成 |
| `remind_settings` | 提醒设置 | 一个人的邮件偏好（一人一行） | 邮件提醒页 |
| `msg_inbox` | 群消息收件箱 | 从群里收到的一条原始消息 | QQ 机器人 |

## courses · 课表

| 列 | 中文名 | 类型 | 说明 |
|---|---|---|---|
| `id` | — | bigint | 主键，自增 |
| `owner_id` | — | text | 归属人，默认 `auth.uid()`，**不要手填** |
| `owner_name` | — | text | 显示名，可空 |
| `name` | 课程名称 | text | 必填 |
| `day` | 星期 | text | `周一` … `周日` |
| `slot` | 节次 | text | `第1-2节` 这种粗粒度写法 |
| `exact_slot` | 精确节次 | text | `1-2` 这种数字写法，用于排时间 |
| `location` | 地点 | text | |
| `teacher` | 教师 | text | |
| `weeks` | 周次 | text | 原样保存老师给的写法，如 `1-14周`、`3-16周 · 双周` |
| `created_at` | — | timestamptz | 创建时间 |

**周次不要自己算。** 页面会解析 `weeks` 里的范围判断这一周上不上，写法越接近教务系统的原文越准。

## ddl_tasks · DDL 任务

| 列 | 中文名 | 类型 | 说明 |
|---|---|---|---|
| `id` | — | bigint | 主键 |
| `owner_id` / `owner_name` | — | text | 归属 |
| `name` | 任务名称 | text | 必填 |

### 提交方式（只能这五个值）

```
在线提交  纸质提交  邮件提交  课堂提交  待确认
```

## plan_stages · 长任务拆解

| 列 | 中文名 | 类型 | 说明 |
|---|---|---|---|
| `id` | — | bigint | 主键 |
| `owner_id` / `owner_name` | — | text | 归属 |
| `total_task` | 总任务 | text | 必填，同一个大作业的所有阶段共用这一个值 |
| `stage_name` | 阶段名称 | text | 建议带序号，如 `2. 需求分析` |
| `deliverable` | 交付物 | text | 这一步做完手上有什么 |
| `planned_start` / `planned_end` | 计划开始 / 完成 | text | 本地日期串 |
| `estimate_basis` | 预估依据 | text | 为什么估这么久，**必须能追溯** |
| `status` | 状态 | text | `未开始` / `进行中` / `已完成` |
| `source_quote` | 来源摘录 | text | |
| `unconfirmed` | 待确认项 | text | |
| `created_at` | — | timestamptz | |

### 状态只有「已完成」是人定的

阶段的「进行中 / 未开始」**不存库**，是页面按链位置推导出来的：

- 链的顺序 = 计划开始时间先后（没排时间的排最后）
- 链头起，连续几个「已完成」之后的第一个 = 进行中，其后一律未开始
- 前序没完成，后序锁死，按钮灰掉

这样永远不会出现「第二阶段在做、第一阶段还没动」的矛盾状态。

所以 `status` 这一列你只会看到 `已完成` 或 `未开始`（完成时写、撤销完成时写回）。
手动把它改成 `进行中` 没有意义——页面不看这个值，它会按链位置重新算。

## remind_settings · 提醒设置

一人一行。同一个人不需要多行。

| 列 | 中文名 | 类型 | 说明 |
|---|---|---|---|
| `id` | — | bigint | 主键 |
| `owner_id` / `owner_name` | — | text | 归属 |
| `remind_email` | 提醒邮箱 | text | 邮件发到这里 |
| `push_time` | 每日推送时间 | text | `07:30` 这种 24 小时制 |
| `daily_digest` | 每日汇总 | boolean | 关掉就整封不发 |
| `due_countdown` | 截止倒计时 | boolean | 关掉后只列今天到期 |
| `long_task_reminder` | 长任务节点提醒 | boolean | 关掉后整块不出现 |
| `advance_days` | 提前提醒天数 | integer | 提前几天开始提醒 DDL，默认 7 |
| `last_push` | 最近推送记录 | text | 上次发送时间，**防止一天发两封** |
| `created_at` | — | timestamptz | |

`last_push` 由发信脚本回写，不要手改。判断逻辑是「今天已经发过就跳过」。

## msg_inbox · 群消息收件箱

| 列 | 中文名 | 类型 | 说明 |
|---|---|---|---|
| `id` | — | bigint | 主键 |
| `owner_id` / `owner_name` | — | text | 归属 |
| `group_name` | 群名称 | text | |
| `sender` | 发送人 | text | |
| `raw_text` | 消息原文 | text | 原样保存，便于回溯 |
| `msg_time` | 消息时间 | text | 机器人带的时刻 |
| `status` | 处理状态 | text | `待处理` / `已处理` / `已忽略` |
| `route` | 去向 | text | 转成了什么：`ddl` / `plan` / `course` / `none` |
| `result_ref` | 结果引用 | text | 指向生成的记录，如 `ddl_tasks#12` |
| `note` | 备注 | text | |
| `created_at` | — | timestamptz | |

**`status` 只认那三个值。** 写成别的（比如 `pending`），那条消息在页面上会直接消失——它被筛选条件过滤掉了，不是数据丢了。

## 每行都属于某个人

所有表都有 `owner_id`，`schema.sql` 里配了行级安全（RLS），四条策略分别是读、增、改、删，条件都是：

```sql
using (owner_id = auth.uid())        -- 读、改、删
with check (owner_id = auth.uid())   -- 增、改
```

意思是：登录用户只能看见和改动 `owner_id` 等于自己的行。**你不需要在前端写任何权限判断**——
就算有人在浏览器控制台里改 JS 去查全表，数据库也只返回他自己的行。

`owner_id` 列有默认值 `auth.uid()`，所以从页面正常写入时**不要自己传这个值**。
只有一种情况需要显式写：直接用 SQL 工具写库时（那条通道不经过登录态，`auth.uid()` 是空的），
这时必须自己带上 `owner_id`，否则会报非空约束错误。

## 三个容易踩的坑

### 1. 枚举词汇必须一字不差

`状态`、`重要度`、`提交方式`、`处理状态` 这几列，写简称或同义词会出问题：

- 页面按精确值筛选，`未完成` 和 `未开始` 是两个字面不同的值，不会互相匹配
- 数据表如果是 `select` 类型，写入不在选项里的值可能被静默改成「待确认」

改这几列时，从页面的下拉框里选，别手打。

### 2. 时间用本地日期串，不要 ISO 格式

```
对：2026-10-25 23:59
错：2026-10-25T23:59:00.000Z
```

页面解析时间只认字面值，不做时区换算。用 ISO 串会差 8 小时，
在东八区表现为「明明晚上 11 点截止，下午 3 点就显示逾期」。

### 3. 加字段要三处一起改

想让课表多一个「学分」字段，需要同时改：

1. `deploy/schema.sql` 加一列（`alter table courses add column credits text default '';`）
2. 页面里的字段映射表 `CLOUD_TABLES` 加一行 `['学分', 'credits']`
3. 表单和卡片的渲染代码里加上这个字段

只改数据库不改映射，页面读不到；只改映射不改数据库，写入会报列不存在。

## 备份与恢复

**备份**：页面顶栏「备份」按钮 → 导出 JSON，包含五张表的全部数据 + 学期锚点。

**恢复**：「数据与账号」抽屉 → 「从备份恢复」→ 选文件。合并规则分两种：

| 当前在哪 | 行为 |
|---|---|
| 云端 | **追加**：把这批记录加进去，不删除任何现有数据 |
| 演示 / 本机模式 | 整库快照的话是**替换**：先清空再写入 |

追加语义意味着重复导入同一个文件会得到重复记录，导入前先想清楚。

文件里的「学期锚点（第 1 周周一）」如果和当前不同，会一并采用——否则换设备后「第几周」会整体错位。

想试一下恢复功能，可以直接拿 `samples/示例备份.json`。

定期备份是个好习惯：云端数据虽然不会丢，但误删是没有回收站的。
