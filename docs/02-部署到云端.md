# 部署到云端

这一步做完，它才从「一个网页」变成「一个应用」：手机验证码登录、数据跟着账号跨设备同步、每人一份互不干扰。

**全程不需要写代码，也不需要买服务器。** 数据库、登录、AI 调用都由 WorkBuddy 云服务托管，你只是在客户端里点几下、回答几句话。

---

## 先理解三件事，省得做到一半发现方向不对

| 事实 | 对你的影响 |
|---|---|
| 云服务应用归属**个人账号**，服务端会校验应用归属 | 你不能借别人的应用写库，必须自己创建一个（免费） |
| 数据库权限靠**行级安全**（RLS）判定 | 同一个网址，每个人登录后只能看到自己的行；你不需要写任何权限代码 |
| 微信账号与手机号账号**是两套身份**，平台不支持合并 | 用哪个登就一直用哪个，两边的数据不相通 |

最后一件事很关键：如果你先用微信登录建了数据，后来改用手机号登录，会看到一个**空账号**，不是数据丢了。
选定一种登录方式后就别换。

---

## 准备工作

- 装好 WorkBuddy 桌面客户端，登录你自己的账号
- 新建一个空工作目录，例如 `C:\Users\你\WorkBuddy\campus`
- 把本仓库的 `campus-workbench.html` 复制进这个目录

**验收**：客户端里打开这个目录，能看到那个 HTML 文件。

---

## 第 1 步 · 创建云服务应用

在 WorkBuddy 里对着这个工作目录说：

> 帮我把这个 HTML 发布成在线应用，需要云数据库和手机号登录

它会走「发布为应用」的流程。发布完成后，你要拿到**两个值**：

| 值 | 长什么样 | 从哪拿 |
|---|---|---|
| `endpoint` | `https://xxxx-12345.app.workbuddy.host` | 发布返回的访问链接，去掉结尾的 `/` |
| `publishableKey` | `wbpk_xxxxxxxx_yyyyyyyy...` | 问它「我的应用 publishableKey 是多少」，或看客户端里的应用详情 |

这两个值**不是秘密**（设计上就是给前端用的公开配置，真正的权限由 RLS 和登录会话决定），
但必须是**你自己这个应用**的那一份。填成别人的，你的数据就会写进别人的库。

> 如果它告诉你「需要先开通云服务」，按提示开通即可。个人使用免费额度足够。

**验收**：浏览器打开那个域名，能看到页面（此时大概率是登录墙或提示连不上，正常——表还没建）。

---

## 第 2 步 · 建五张表

五张表的结构写在 `deploy/schema.sql` 里，逐列和页面代码对得上，**建完不需要改任何前端代码**。

在 WorkBuddy 里说：

> 读 `deploy/schema.sql`，用 `workbuddy_cloudservice_db_exec_sql` 一条一条执行，
> applicationId 用 `wbapp_你的应用ID`，mode 全部用 `migrate`，全部执行完告诉我结果。

几点要注意：

- 脚本里用 `-- ─── 语句 N ───` 分组，但**每一条以 `;` 结尾的 SQL 都要单独执行**。工具一次只吃一条，整段粘贴会失败。共 21 条。
- 全部用 `mode: "migrate"`（建表和改权限必须走这个角色）。
- 脚本是**幂等**的：重复跑不会报「表已存在」「策略已存在」。

**验收**：问它「列出我的表」，应该看到五张：

```
courses            课表
ddl_tasks          作业与考试截止
plan_stages        长任务拆解
remind_settings    邮件提醒设置
msg_inbox          群消息收件箱
```

每张都应该是「已开启行级安全」。

> **为什么 SQL 里既要写 policy 又要写 grant？**
> 这是两道独立的门。只写 policy 不写 grant，登录用户根本碰不到表，报错 `42501`；
> 只写 grant 不写 policy，那就是所有人能读写所有人的数据。两道门都过了才正确。

---

## 第 3 步 · 把两个值填进页面

打开 `campus-workbench.html`，搜索 `var CLOUD_CFG`，会看到：

```js
var CLOUD_CFG = {
  endpoint: '',
  oauthRelayBaseUrl: 'https://www.workbuddy.cn/v2/as/genie-baas/oauth',
  publishableKey: ''
};
```

填成：

```js
var CLOUD_CFG = {
  endpoint: 'https://你的域名.app.workbuddy.host',
  oauthRelayBaseUrl: 'https://www.workbuddy.cn/v2/as/genie-baas/oauth',
  publishableKey: 'wbpk_你的_那一串'
};
```

- `endpoint` **结尾不要带 `/`**
- `publishableKey` 必须和 `endpoint` 属于同一个应用
- `oauthRelayBaseUrl` **一个字都不要动**，那是平台统一的登录中转地址
- 两个值任意一个为空，页面就会退回演示模式（本地示例数据），不会报错

**验收**：保存文件后，在本地起个服务打开它，此时应该出现登录墙而不是演示数据。这说明配置生效了。

---

## 第 4 步 · 重新发布

改完配置必须再发布一次，否则线上还是旧文件。

> 再发布一次，同一个目录、同一个应用

因为目录和应用没变，**域名不会变**，之前发出去的链接继续有效。

**验收**：打开域名 → 出现登录页 → 用手机号登录（首次自动注册）→ 进主界面 → 手动加一门课 → 刷新，课还在。

这一步同时会生成你的 `owner_id`，如果之后要接 QQ 机器人会用到它。

---

## 第 5 步 · 确认数据真的在云端

做一次交叉验证，别只看单端：

1. 电脑上加一门课
2. 手机浏览器打开同一个域名，登录同一个账号
3. 手机上能看到那门课 → 说明跨设备同步通了

再看一眼隔离是否正确：

4. 换一个从没用过的手机号登录
5. 应该看到**空课表**，看不到第 1 步加的那门课

第 5 步是重点。如果新账号能看到别人的课，说明 RLS 没生效，立刻停下来检查第 2 步的 grant 是否都执行了。

---

## 之后怎么更新

上游更新了页面，你只要替换 `campus-workbench.html` 再发布一次即可。
**但替换后必须把 `CLOUD_CFG` 那两个值重新填回你的**——上游那份是空的，不填就会退回演示模式。

建议做法：把你的两个值抄在一个顺手的地方（密码管理器或笔记），每次更新时对照填一次。

---

## 排错

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 打开是演示模式，没有登录页 | `CLOUD_CFG` 两个值没填全，或填完没重新发布 | 检查两个值都非空，再发一次 |
| 登录页一直转圈 / 提示加载不到组件 | 网络不通、广告拦截插件拦了 SDK | 换网络、关掉拦截插件重试 |
| 能登录但页面全是空 | 表没建，或者建表用的是别的应用 | 用第 2 步的验收清单核一遍 |
| 加数据报 `42501` | 漏了 `grant` 语句 | 单独补跑 `schema.sql` 里第 11–15 条 |
| 加数据成功但刷新就没了 | 写到了别人的库，被 RLS 过滤掉 | 检查 `endpoint` 和 `publishableKey` 是否属于同一个应用 |
| 手机号收不到验证码 | 号码格式或当日发送次数限制 | 确认 11 位、稍等再试 |
| 微信登录在手机上扫不了 | 微信的设计：手机浏览器只给二维码 | 用另一台设备扫，或直接用手机号登录 |

更多问题见 [常见问题](06-常见问题.md)。
